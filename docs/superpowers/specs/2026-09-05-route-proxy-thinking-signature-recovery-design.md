# 路由代理恢复被拒绝的 thinking 签名设计

## 1. 背景

Claude Code 开启扩展思考后，会在之后每一轮的 assistant 历史里原样回放 `thinking` 块。而 `thinking` 块的 `signature` 只对签发它的那个上游有效。

算力池按 `route_priority` 分组、组内轮询选账号，并且在一次成功之后把游标推进到刚服务过的账号之后（`route_proxy_service.rs` 成功路径保存 cursor 的两处）。也就是说，同一个会话的相邻两轮**天然落在不同账号上**。于是第一轮之后的任意一轮，只要落到另一个账号——尤其是把请求重签进 Bedrock `InvokeModelWithResponseStream` 的中转站——就会被拒：

```
ValidationException: messages.N.content.0: Invalid `signature` in `thinking` block
```

这类 400 目前走语义失败分支：先按账号的 `retry_count` 在同一个账号上**原样**重发（必然以同样理由失败），再把 `semantic_response_transient` 记到账号/模型上（把一个完全可用的模型冷却掉），然后换下一个账号重复同样的过程。N 个账号就是 3N 次注定失败的上游请求，最后客户端收到聚合出来的 502，会话彻底卡死；账号列表还会把这条 Bedrock 报错当成**这个账号的**失败消息展示给用户。

模型映射按账号各自配置，因此"同名模型映射到不同上游模型"同样会让签名失效，属于同一类问题。

## 2. 目标

- 识别「回放的推理块签名被拒」这一类失败，并且只识别这一类。
- 自动恢复：剥掉 assistant 历史里的 `thinking` / `redacted_thinking`，用同一个账号重发一次；恢复成功时客户端只看到成功响应。
- 不把这类失败计入账号或模型：不改 `status`、不累加临时失败、不写 `last_failure_message`。
- 不再遍历账号池——池里其他账号会以完全相同的理由拒绝同一段历史。
- 恢复不了时，把上游的原始响应交回客户端，而不是聚合后的 502。

## 3. 非目标

- **不做会话粘性路由。** 把一个会话钉在同一个账号上能从根上避免签名跨账号，但代理目前完全不解析请求里的会话标识（`metadata.user_id` 里的 `session_id` 无人读取），粘性还会与优先级、并发上限、冷却回避互相打架。若本方案的一次重试在实践中仍显不足，再单独设计。
- 不改其他失败类型的状态规则、重试预算与冷却规则。
- 不新增前端开关或配置项。

## 4. 方案

### 4.1 识别

`response_failure_service::is_thinking_signature_failure` 判定一段文本是否在讲「回放的推理块被拒」：规范化后同时出现 `thinking` 与 `signature`，且带有无效标记（`invalid` / `无效` / `verification failed` / `does not match` / `is required`）。

之所以不匹配单一句式：各中转站措辞不同，且都会把真正的报错裹在自己的散文里（示例里的 `error.type` 甚至是被格式化进 JSON 的 Go nil，类型规则完全看不见它）。要求 `thinking` 同时出现，可以把请求签名、TLS 一类同样含 "signature" 的错误挡在外面。签名**缺失**也归到这一类：成因与补救完全相同。

判定只读 `detect_response_failed` 解析出来的 `error.message`，不扫原始响应体：流式响应体里本来就带着 `signature_delta` 帧，扫原始体会把「中途失败的正常思考流」误判成签名被拒。

### 4.2 改写

`anthropic_thinking::strip_replayed_thinking` 从 Anthropic 请求体的 assistant 历史里删除 `thinking` / `redacted_thinking` 块，并返回请求体是否真的变了（没变就不该花掉一次重试去重发上游已经拒过的请求）。两个附带规则：

- 只剩空 `content` 的 assistant 消息整条删掉——空 `content` 不是合法消息，而连续同角色消息是合法的。
- 如果最新的 assistant 轮次带 `tool_use`，同时把 `thinking` 降为 `disabled`。开启思考时这样的轮次必须以思考块开头，剥掉之后不降级就会换个理由再被拒一次。客户端没要求思考时不会凭空写入该字段。

入站桥接早就在对同一段历史做同样的事（`route_protocol_bridge::claude_responses` 等三处都直接丢弃回放的思考块），本方案只是把这套处理补到原生 Anthropic 直通路径上。

### 4.3 边界与预算

- 每个客户端请求最多改写一次。请求体只会被剥薄，第二次改写找不到东西可剥，重发等于原样重试。
- 改写后的重试仍是**同一个账号**，并且不消耗该账号的 `retry_count` 预算——这一次问的是另一个问题。
- 改写标记只存在于单次客户端请求内，不落库。
- 失败的首次尝试照旧写入请求统计与实时日志（重试用的是改写后的请求体，日志里能直接看出改了什么），但不写任何账号/模型失败状态。

## 5. 代码边界

- `response_failure_service`：新增识别函数，保持纯函数与单元测试。
- `anthropic_thinking`（新模块）：请求体改写，纯函数，附字节层包装供代理调用。
- `route_proxy_service`：重试循环里新增一条分支，位置在配额、永久失效、语义失败之前；`body_bytes` 改为可变以便替换。
- 前端与数据库：不改。这类失败不再落到账号上，账号列表的失败提示无需新增文案。

## 6. 测试计划

- 单元测试：真实上报的 Bedrock 报文可被识别；其他措辞同样可识别；只含 `signature`（请求签名）或只含 `thinking`（推理参数报错）的消息不被识别。
- 单元测试：剥离保留用户原话与 `tool_use`、删除只剩推理的轮次、`tool_use` 轮次触发 `thinking` 降级、无可剥内容时报告未改动、非 JSON 请求体不改写。
- 代理集成测试：上游首次以真实报文拒绝、之后成功时，客户端收到成功响应，上游只被调用 2 次，第二次请求体不含推理块且 `thinking` 已降级，账号与模型都不被记失败。
- 代理集成测试：上游始终拒绝、池里有两个账号时，客户端收到上游原始的 400（而不是 502），上游只被调用 2 次（第二个账号完全不被打扰），两个账号都不被记失败。
- 回归：运行 Rust 全量测试，确认过载重试、可重试状态码、语义失败等既有规则不变。
