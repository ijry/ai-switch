# 账号临时失败状态与可配置冷却设计

## 背景

账号发生可重试的联系请求失败时，数据库已经记录临时失败次数，但账号行仍只显示生命周期状态，用户无法快速判断账号近期是否持续失败。同时，失败冷却目前按 30 秒、2 分钟和 10 分钟逐级退避，响应时间偏长且无法按账号调整。

## 目标

- 临时失败期间在账号状态区域显示 `错误 N 次`。
- 最近一次请求成功时清除临时失败计数、失败时间和失败元数据，状态标签自然恢复为账号原本的正常状态。
- 失败冷却改为固定时长，每次触发均使用账号失败处理策略中的 `cooldown_seconds`。
- `cooldown_seconds` 缺失时兼容旧账号并默认 10 秒，可在账号编辑的“失败处理策略”中配置。
- 保持 `retry_interval_ms` 作为同一次请求内部重试间隔，不与账号冷却混用。

## 行为

### 临时失败状态标签

`transient_failure_count > 0` 时，账号行显示 `错误 N 次`，其中 N 为数据库中的临时失败次数。该标签只替换正常生命周期状态的展示；`revoked`、`error`、`paused` 等明确生命周期状态仍按原标签显示，避免隐藏永久状态。

成功路径调用现有 `clear_transient_failure`，清除计数、`next_retry_at`、`cooldown_until`、最后失败信息和语义失败 streak，因此下一次渲染显示正常账号状态。

### 固定冷却

失败处理策略新增：

```json
{
  "cooldown_seconds": 10
}
```

启用 `cooldown_enabled` 后，每次记录临时失败都以当前时间加配置秒数生成 `next_retry_at` 和 `cooldown_until`。不启用冷却时仍累计失败次数，但两个时间字段保持为空，账号不因该开关而暂时退出路由。

允许值为 1 到 86,400 秒；缺失字段、旧配置和前端无法识别的值回退到 10 秒。策略解析和保存沿用现有账号级配置格式。

## 测试

- 缺失策略字段默认 `cooldown_seconds = 10`。
- 显式配置值被读取并保留。
- 零值和超过上限的值被拒绝。
- 启用冷却后第 1、2、3 次失败均产生约配置时长的固定冷却，而非旧的渐进时长。
- 成功清除临时失败计数及冷却字段。
- 前端显示 `错误 N 次`，成功/计数为零时显示原状态标签。
