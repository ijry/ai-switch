# 账号模型列表本地持久化设计

## 背景

API 账号在新增或编辑时可以向上游请求模型列表，用于模型映射输入提示和“一键设置”。当前获取结果只保存在弹窗的 React 临时状态中；关闭弹窗后结果丢失，再次编辑同一账号时必须重新请求上游。

本次改动让已获取的模型列表跟随账号保存在本地。用户保存账号后，再次编辑时可直接复用上次成功获取的列表，同时仍可手动刷新。

## 目标

- 成功获取的模型列表随 API 账号保存到本地。
- 打开 API 账号编辑弹窗时直接回填已保存的模型列表，不自动发起网络请求。
- 手动重新获取成功后，以新列表替换弹窗中的旧列表，并在保存账号时落盘。
- 会影响上游模型范围的连接配置发生变化时，清空弹窗中的旧列表，避免错误复用。
- 兼容没有本地模型列表字段的现有账号和异常历史数据。
- 账号复制、导出和导入继续依赖现有 `config_json` 流程，自然携带模型列表。

## 非目标

- 不为模型列表增加自动刷新周期或后台刷新任务。
- 不在点击“获取模型列表”时立即修改已保存账号；只有保存账号后才落盘。
- 不新增独立的模型目录页面或模型列表管理界面。
- 不为官方登录账号增加本次 API 模型列表缓存能力。
- 不新增数据库表或数据库列。

## 方案选择

### 采用方案：嵌入账号 `config_json`

在 API 账号现有 `config_json` 中增加可选的 `fetched_models` 数组。该配置已经随账号在数据库、复制、导入和导出流程中传递，能够满足“模型列表跟随账号”的要求，而且无需数据库迁移。

每个有效条目至少包含非空字符串 `id`，并可保留获取接口返回的 `owned_by`、`supports_1m` 等受支持元数据。读取时只接受结构有效的条目；字段缺失、JSON 无效或条目无效时按空列表或跳过无效条目处理，不能阻止账号编辑。

### 未采用方案

- 独立数据库字段：数据边界清晰，但需要数据库迁移，并修改账号查询、复制、导入、导出和传输结构，改动面与本需求不相称。
- 浏览器本地缓存：实现简单，但无法可靠跟随账号复制、导入导出或跨运行环境迁移，不符合“跟随账号存储”的语义。

## 数据结构

API 账号配置示例：

```json
{
  "base_url": "https://api.example.com/v1",
  "interface_format": "openai",
  "model_mappings": [],
  "fetched_models": [
    {
      "id": "gpt-5",
      "owned_by": "example"
    }
  ]
}
```

`fetched_models` 是辅助编辑的数据，不参与路由账号选择或模型映射执行。现有运行时读取 `config_json` 时应继续忽略不需要的额外字段。

新增 API 账号的后端输入增加可选的 `fetched_models_json: Option<String>` 载荷。服务端负责校验其为 JSON 数组，且每个条目都有非空字符串 `id`；载荷不是合法 JSON、不是数组或包含结构非法条目时返回校验错误，不创建账号。未提供时写入空数组或省略该字段，读取语义均为空列表。编辑账号继续通过完整 `config_json` 更新，无需增加新的更新命令。

## 前端行为与数据流

### 新增账号

1. 用户填写 API Key、Base URL、接口格式和鉴权字段。
2. 用户点击“获取模型列表”，前端使用当前连接配置请求上游。
3. 请求成功后，模型列表进入新增弹窗状态，供输入提示和“一键设置”使用。
4. 用户点击“保存账号”时，前端将当前模型列表与模型映射一并提交。
5. 批量创建多个 API Key 时，现有逻辑仍使用第一个 API Key 获取模型列表，并将同一份列表保存到本次创建的每个账号。
6. 用户取消新增时，不保存模型列表。

### 编辑账号

1. 打开 API 账号编辑弹窗时，从 `config_json.fetched_models` 解析并回填模型列表。
2. 回填过程不调用上游接口，界面直接显示已保存的模型数量，并继续支持输入提示和“一键设置”。
3. 用户手动点击“获取模型列表”后，请求成功则替换弹窗中的列表；请求失败则保留当前有效列表并显示错误。
4. 用户点击“保存修改”后，将弹窗中的当前模型列表写回 `config_json.fetched_models`。
5. 用户取消编辑时，不修改账号中已保存的列表。

## 缓存失效规则

以下字段会改变请求身份或模型列表来源，其值被用户修改时清空弹窗当前模型列表和获取错误：

- API Key；
- Base URL；
- 接口格式；
- Anthropic/Claude 鉴权字段；
- 可直接编辑的 Secret JSON 或 Config JSON。

User-Agent、模型映射、失败处理策略、路由优先级、最大并发数等不会改变模型列表请求来源，因此修改这些字段时不清空列表。

清空只影响当前弹窗状态。只有用户随后保存账号，空列表才会覆盖账号中原有缓存；取消编辑仍保留原有已保存列表。

## 错误处理与兼容性

- 上游请求失败：显示现有错误信息，不覆盖仍然有效的弹窗模型列表。
- `config_json` 没有 `fetched_models`：按空列表处理。
- `fetched_models` 不是数组：按空列表处理。
- 数组中存在无效条目：忽略无效条目，保留其他有效条目。
- 老版本应用读取带有 `fetched_models` 的账号配置时，额外字段不应影响既有路由行为。
- 模型列表不包含 API Key、访问令牌或其他秘密信息，不写入 `secret_payload_json`。

## 组件边界

- 前端解析辅助函数：只负责从 `config_json` 提取并规范化 `fetched_models`。
- 前端配置序列化函数：负责在保留账号其他配置字段的同时更新 `fetched_models`。
- 新增账号服务输入：负责把可选模型列表安全写入新账号配置。
- 现有更新账号流程：继续接收完整配置，不增加额外持久化通道。

这样可以让模型列表持久化逻辑独立于模型映射生成和上游请求实现，后续调整列表格式时不会改变路由核心行为。

## 测试策略

### 前端测试

- 新增 API 账号获取模型列表后，保存请求包含模型列表。
- 新增 API 账号未获取模型列表时，保存空列表且行为与当前一致。
- 编辑带有 `fetched_models` 的账号时，直接显示已保存数量，且不会调用 `fetchRouteModels`。
- 编辑账号手动刷新成功后，保存的新配置包含新列表。
- 手动刷新失败时，已回填列表仍然存在。
- 修改 API Key、Base URL、接口格式或鉴权字段后，列表被清空。
- 缺失、格式错误或包含无效条目的缓存不会导致编辑弹窗崩溃。

### 后端测试

- 创建 API 账号时，合法模型列表写入 `config_json.fetched_models`。
- 未提供模型列表时保持向后兼容。
- 非数组或结构非法的新增载荷被服务端拒绝，且错误不会创建半成品账号。
- 账号复制后仍保留 `fetched_models`。

### 验证命令

- `pnpm typecheck`
- `pnpm test:run -- tests/AccountsScreen.test.tsx`
- 与 Rust 输入结构和服务改动相关的定向 `cargo test`

## 验收标准

- 用户获取模型列表并保存 API 账号后，关闭再打开编辑弹窗，无需联网即可看到并使用该列表。
- 打开编辑弹窗本身不会触发模型列表请求。
- 修改模型列表来源配置后不会继续使用旧列表。
- 现有账号、账号复制和账号导入导出流程不因新增字段而退化。
