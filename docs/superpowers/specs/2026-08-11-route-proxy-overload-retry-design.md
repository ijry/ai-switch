# 路由代理上游过载自动重试设计

## 1. 背景

部分上游会返回 HTTP 成功状态，但响应体携带 `response.failed`，错误消息为：

`Our servers are currently overloaded. Please try again later.`

这表示上游服务暂时繁忙，并不表示当前账号凭证失效。当前代理已经将该错误排除在账号 `error` 状态之外，但账号池只有一个账号时，失败会直接暴露给客户端。

## 2. 目标

- 仅对明确识别为“服务器过载”的语义失败执行自动重试。
- 每个账号在一次客户端请求期间最多额外重试 5 次，即单个账号最多尝试 6 次。
- 每次过载后仍允许按现有账号池顺序切换到其他账号；每个账号拥有独立的 5 次重试预算。
- 重试成功时，客户端只收到成功响应，不感知中间过载错误。
- 重试失败时，账号保持现有状态，不被标记为 `error`、`paused` 或 `revoked`；仅记录临时失败和退避信息。
- 非过载的 `response.failed`、认证失败、固定窗口额度耗尽等错误继续使用现有状态规则。

## 3. 非目标

- 不对所有 `response.failed` 统一重试。
- 不改变固定窗口额度耗尽的自动暂停规则。
- 不改变永久认证错误的撤销规则。
- 不新增前端重试开关或配置项。

## 4. 方案

### 4.1 重试边界

在路由代理的单次请求循环中，为当前账号维护过载重试次数。检测到过载语义失败后：

1. 记录一次临时失败。
2. 若当前账号尚未达到 5 次额外重试预算，则等待短暂退避并再次请求同一账号。
3. 达到预算后，结束当前账号尝试并切换到下一个账号。
4. 每个账号切换后重新从 0 开始计算该账号的重试次数。

重试预算仅存在于当前客户端请求内，不写入数据库；数据库中的 `transient_failure_count` 只用于现有冷却和可观测性。

### 4.2 退避

使用有限的短退避，避免在上游过载时形成紧密请求循环。默认等待序列为 300ms、1s、2s、3s、5s，并限制单次请求的总处理时间，避免客户端无限等待。

如果请求已经接近代理层的超时边界，则跳过剩余重试并进入下一个账号。

### 4.3 状态与客户端响应

- 过载重试成功：清理该账号临时失败信息，返回上游成功响应。
- 当前账号重试耗尽：切换账号，不改变账号业务状态。
- 所有账号都重试耗尽：沿用现有代理错误聚合响应，将最终失败返回客户端。
- 过载错误的响应体仍写入请求统计和实时日志，但不会写入 `semantic_response_failed` 状态记录。

显式模型测试沿用同一过载识别规则，但不复用代理请求的重试计数；模型测试调用仍按当前测试服务的单次账号语义执行，失败只记录临时失败。

## 5. 代码边界

- `response_failure_service`：负责识别过载语义错误，保持纯函数和单元测试。
- `route_proxy_service`：维护每个账号在单次请求内的重试计数、退避和账号切换。
- `route_credential_repository`：继续使用现有临时失败记录接口，不新增状态类型。
- `route_model_test_service`：保持过载错误不升级为 `error`，不改变现有显式测试流程。

## 6. 测试计划

- 单元测试：过载消息识别、大小写和多余空白处理。
- 代理集成测试：单账号前 5 次过载、第 6 次成功时，客户端收到成功响应且上游被调用 6 次。
- 代理集成测试：单账号始终过载时，调用次数为 6，账号状态仍为 `ok`，最终错误才返回客户端。
- 代理集成测试：第一个账号重试耗尽后切换第二个账号，第二个账号独立拥有 5 次预算。
- 回归测试：非过载 `response.failed` 仍设置 `error`；固定窗口额度码仍设置 `paused`；永久认证错误仍设置 `revoked`。
- 运行前端类型检查、前端测试、Rust 格式检查和 Rust 单元测试。
